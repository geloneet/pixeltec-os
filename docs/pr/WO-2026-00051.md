# WO-2026-00051 — Control de acceso de mínimo privilegio para Meta App Review (rol `reviewer`)

Rama `feature/meta-review-access-control` desde `origin/main` `b5601fd`. Sin push, sin deploy, sin crear la cuenta, sin tocar la DB de prod.

## 1. Diseño (PASO 1)

### Hechos verificados en código (`b5601fd`)

- Roles `admin | staff` (`src/lib/db/schema.ts:49`, enum `user_role`). Autoridad en Postgres por request: `resolveAuthority` (ADR-0036) — la usa `requireAdmin`, `requireUserSession`, `getSessionUserId` **y el callback `jwt`** (`auth.config.ts`), que refresca `token.role` desde la base en cada reemisión y destruye la sesión si la base la niega (fail-open solo ante error de DB).
- `src/middleware.ts:62` exige únicamente sesión sobre `PROTECTED_PATHS` (15 slugs de `ADMIN_ROUTES`); `/api/*` y las server actions no pasan por ningún gate de rol en middleware.
- 17 rutas / 21 handlers en `/api/whatsapp-inbox/**` en `main` usan `requireAdmin` (staff ya recibe 403 ahí hoy); el 22.º (`GET /coexistence/status`) está en la rama de WO-2026-00047, sin mergear.
- La UI de `/whatsapp` (`WhatsAppModule` + hooks) consume **solo** `/api/whatsapp-inbox/*` — cero server actions. El shell `(admin)/layout.tsx` sí invoca server actions al montar (`getMyNotifications`, `getCrmDataAction`), todas con `try/catch` → degradan sin romper la página.
- Las server actions se invocan con `POST <ruta actual>` + header `Next-Action: <id>`: un usuario en `/whatsapp` puede invocar **cualquier** action del bundle (CRM, documentos, contacto…) — la mayoría solo exige sesión (`getSessionUserId`). Ocultar la UI no protege nada.

### Opciones

| | Solución | Por qué sí / por qué no |
|---|---|---|
| **A (elegida)** | Nuevo valor `reviewer` en `user_role` (migración aditiva) + **deny-by-default central en middleware** para roles restringidos + guard explícito `requireWhatsAppReviewAccess` (admin ∨ reviewer) **solo** en la allowlist de `/api/whatsapp-inbox` | Reutiliza la autoridad existente (`users.role` leído de Postgres en cada request); `requireAdmin` queda intacto; una sola tabla de política pura y testeable (`src/lib/routes/reviewer-access.ts`); invitar/asignar desde `/usuarios` con las mismas actions. Coste: 1 `ALTER TYPE … ADD VALUE IF NOT EXISTS`. |
| B | Allowlist por cuenta (email) o por capacidad | Por email = credencial en config/env o tabla nueva y una segunda fuente de autoridad distinta a `users.role`; por capacidad = RBAC granular (Miguel lo excluyó). |
| C | Flag `users.is_reviewer` / status nuevo | Igual de invasivo en DB que A (columna o valor de enum) pero con dos fuentes de rol; el enum ya es el punto único que leen `resolveAuthority`, `/usuarios` y el JWT. |

### Política del rol restringido (fail-closed)

`isRestrictedRole(role)` = `role !== "admin" && role !== "staff"` — cualquier rol desconocido/futuro cae en mínimo privilegio; admin y staff conservan exactamente el comportamiento actual.

En `middleware.ts`, con sesión de rol restringido, en este orden:

1. **Server action** (header `next-action` presente) en cualquier path → **403**.
2. `/api/*` → solo `/api/auth/*` (NextAuth: session/csrf/signout — imprescindible para el login/logout existente), `POST /api/csp-report`, y la allowlist explícita `método + path` de abajo → resto **403**.
3. Página bajo `PROTECTED_PATHS` → solo `/whatsapp` y subrutas; `GET /hoy` (aterrizaje por defecto tras login, sin tocar el flujo de login) → **302 → /whatsapp**; resto (`/usuarios /cobros /clientes /vps /accesos /ia-factory /documentos /blog-admin /smilemore-respuestas /proyectos /perfil /notificaciones /crecimiento`) → **403**.
4. Cualquier método distinto de `GET/HEAD/OPTIONS` fuera de la allowlist → **403**.
5. Superficie pública (landing, blog, `/login`, estáticos de `/public`) → igual que un anónimo: no es privilegio.

Segunda capa (server-side, independiente del middleware): `requireWhatsAppReviewAccess` en los handlers de la allowlist relee `resolveAuthority` (Postgres) y acepta `admin | reviewer`; `staff` sigue 403 como hoy. Los 9 handlers excluidos conservan `requireAdmin` (reviewer → 403 aunque el middleware fallara).

### JWT stale tras cambio de rol

`token.role` se refresca desde Postgres en cada request (callback `jwt`); además `setUserRoleAction` estampa `sessions_valid_from` (`revokeCredentialsFor`) cuando la transición **entra o sale** de `reviewer`, así todo token previo muere en las fronteras fail-closed (`resolveAuthority` → `credentials_changed`). Admin↔staff no cambia de comportamiento.

### Comportamientos intencionales (confirmados por el SG)

- **`/perfil` bloqueado** para el reviewer (403): no cambia su contraseña ni gestiona 2FA; la rotación la hace Miguel por invitación/suspensión desde /usuarios.
- **Server actions**: 403 para el reviewer en cualquier path. El shell `(admin)` las invoca al montar (`getMyNotifications`, `getCrmDataAction`) dentro de `try/catch`: la campana queda vacía y el CRM sin datos; `/whatsapp` no depende de ninguna.
- **Botones excluidos en la Console** (guardar/publicar/rollback de configuración, notas, tickets, ejemplos): reciben 403 y muestran el error saneado existente de `toInboxFailure`; el módulo sigue renderizando y operando en lectura + envío + modo.
- **Rol desconocido o ausente en la sesión** ⇒ restringido (fail-closed); admin y staff ⇒ exactamente como antes.

### Migración 0042 — plan de aplicación en prod y rollback

- **Archivo:** `drizzle/0042_user_role_reviewer.sql` · `sha256 = fb5f65f4f5cb433072639839e7eb2185aedf7e430e9c627ff729ce049add4a78` · journal `when = 1787674359079` (`idx 42`).
- **Aplicación (antes de arrancar la imagen nueva; patrón de reconciliación de `01_CONTEXT/infraestructura.md`, contenedor `pixeltec-os-db` 127.0.0.1:5437, user/db `pixeltec_os`):**
  1. `docker exec -i pixeltec-os-db psql -U pixeltec_os -d pixeltec_os < drizzle/0042_user_role_reviewer.sql`
  2. `INSERT INTO drizzle.__drizzle_migrations (hash, created_at) VALUES ('fb5f65f4f5cb433072639839e7eb2185aedf7e430e9c627ff729ce049add4a78', 1787674359079);`

- **Riesgo de aplicación:** nulo para cuentas existentes (no toca filas). Idempotente (`IF NOT EXISTS`).
- **Rollback:** Postgres no permite quitar un valor de enum. El valor puede quedar inerte **pero el código ANTERIOR (`b5601fd`) trata `reviewer` como «no admin» = acceso tipo staff, NO como denegado**. Por tanto, ANTES de volver a la imagen anterior: `UPDATE users SET role = 'staff', status = 'suspended', sessions_valid_from = now() WHERE role = 'reviewer';` (deja constancia en `security_events` manualmente si procede) y solo después desplegar el SHA previo. Sin cuentas `reviewer`, el valor extra del enum no tiene ningún efecto en el código viejo (Drizzle no valida enums al leer).

## 4. Pendientes / riesgos

- **Cuenta `meta-review@pixeltec.mx`: NO creada** (por orden). Flujo previsto: /usuarios → Invitar → rol «Revisor externo (solo WhatsApp)» → la persona fija contraseña por el enlace → entra por /login → aterriza en /whatsapp.
- **Veredicto visual (ING-001) pendiente:** no se levantó servidor ni se hizo login con cuenta real; el comportamiento del shell para el reviewer (sidebar sin áreas, campana vacía, Console con botones de escritura → 403 con toast) está verificado por tests, no en navegador.
- `src/app/(admin)/perfil/page.tsx` muestra «Staff» para un reviewer (fuera de scope; irrelevante porque el reviewer no puede abrir /perfil).
- `src/hooks/use-user-profile.ts` tipa `role` como `'admin' | 'staff'` (cast, sin efecto en runtime; fuera de scope).
- Durante un outage de Postgres el callback `jwt` conserva el token (fail-open documentado): el middleware decide con el último rol sellado. Para una cuenta creada como `reviewer` ese rol es siempre `reviewer`; las rutas de la allowlist además fallan cerrado (`resolveAuthority` lanza → 5xx, no acceso).
- `GET /api/whatsapp-inbox/coexistence/status` llegará con WO-2026-00047: el contrato exige cambiar su guard a `requireWhatsAppReviewAccess` al mergear (hoy usa `requireAdmin` en esa rama → el reviewer vería «No disponible» en la tarjeta).
